# 管理员小程序审批与数据体验审查设计

日期：2026-07-15  
状态：用户已确认方案 B，待实施计划

## 一、目标与范围

本轮优化面向超级管理员、书院辅导员和导生管理员，解决管理员小程序在审批判断、角色重点、统计口径、页面状态和导航体验上的问题。

范围包含：

- 普通预约审核与辅导员重点审核；
- 管理员专用预约详情；
- 管理员首页、管理中心、数据统计和账号设置；
- 三类角色的楼栋范围与功能边界；
- 小程序和后台共用接口的数据一致性；
- 加载、失败、空状态、重复提交与并发刷新保护；
- 管理员小程序回归检查及真实接口验收。

本轮不增加复杂排班、批量审批、空间配置、账号管理等桌面端高级管理能力，也不改变宿生端预约主流程。

## 二、审查证据与结论

审查证据保存在 `docs/audits/2026-07-15-miniapp-admin/`：

1. `01-super-admin-approval-home.png`：普通与重点审核入口样式缺失、标题重复、审批依据不足。
2. `02-admin-stats-broken-ranking.png`：房间名称和使用数据缺失，百分比含义不成立。
3. `03-admin-management-center.png`：审批名称模糊，重点与普通任务缺少数量区分。
4. `04-admin-profile.png`：标题与栏目不一致，存在偏开发人员的“网络诊断”表述。
5. `05-guide-admin-approval-home.png`：导生管理员只能看到普通队列，但开放房间数错误使用全院数据。

代码与接口核对进一步确认：

- 管理员首页同时读取审核队列、公开房间统计和反馈数据，统计口径不统一；
- `/room/stats` 未按管理员楼栋范围统计，导致楼栋导生账号看到全院开放房间数；
- 模拟数据模式下 `/stats/usage-rate` 返回结构与页面字段不一致；
- 当前“使用率”实际由预约次数除以 30 得出，不代表空间使用率；
- 审批列表加载失败后被静默转换为空列表，管理员无法区分“暂无待办”和“加载失败”；
- 管理员从“全部预约”进入的是宿生版详情，存在不适合管理员的操作和文案；
- 底部管理员导航通过重新启动页面切换，会丢失当前状态；
- 现有自动检查验证了接口和权限，但没有覆盖上述显示语义、数据口径和审批决策安全。

## 三、角色与审批工作台

### 3.1 角色默认行为

- 导生管理员：只显示“普通预约审核”，数据受账号的全院或具体楼栋范围限制。
- 辅导员：默认进入“重点预约审核”，同时可切换查看普通预约。
- 超级管理员：可查看两个队列，首页同时显示普通待审数与重点待审数，默认优先展示重点预约。

角色切换或异步请求返回后，页面必须再次校验当前角色，禁止旧角色请求覆盖新角色页面。

### 3.2 队列切换

普通与重点队列使用页面内分段切换，不再通过导航到同一页面生成新的页面栈。切换时保留页面结构，只刷新目标队列和对应数量。

每个队列必须有四种明确状态：

- 首次加载；
- 正常列表；
- 真正无待办；
- 加载失败，可重试。

失败状态不得显示为“暂无待审批预约”。

### 3.3 普通预约卡片

普通预约面向高频处理，卡片直接显示：

- 预约人姓名和学号；
- 房间、房间类型和所属楼栋；
- 日期与时间段；
- 预约用途；
- 参与人数；
- “普通待审”状态标签。

管理员可点击卡片查看完整详情，也可在卡片上快速通过。快速通过仍需二次确认；拒绝必须填写非空原因。

### 3.4 辅导员重点预约

重点预约使用显著但不过度警示的重点标签，展示触发重点审核的空间类型、用途、人数和时间。

重点预约不提供卡片直接通过按钮。辅导员或超级管理员必须进入管理员专用详情页，查看完整申请信息和宿生信用状态后才能处理。拒绝必须填写原因。

该要求只约束 `counselor_pending`，不降低辅导员处理普通待审预约的效率。

### 3.5 操作反馈

- 审批进行中时仅锁定当前预约，防止重复提交；
- 成功后刷新当前队列、两个待办数量和相关统计；
- 若预约已被其他管理员处理，提示刷新结果，不显示通用“操作失败”；
- 请求失败时保留原卡片，允许重试；
- 拒绝理由不因一次提交失败而丢失。

## 四、管理员专用预约详情

新增管理员专用详情页，不复用宿生预约详情页。

详情内容分为：

1. 审批状态：普通待审、重点待审、已通过、已拒绝等；
2. 预约信息：房间、楼栋、空间类型、日期、时间、用途、人数、提交时间；
3. 预约人信息：姓名、学号、信用分与账号状态；
4. 审批提示：说明当前预约属于普通审核还是重点审核；
5. 审批操作：按角色和预约状态显示通过、拒绝或只读结果。

详情页不得出现“取消我的预约”“我的预约”“返回宿生首页”“查看签到凭证”等宿生操作。接口加载失败时不得生成虚构的备用预约数据。

## 五、首页和统计口径

### 5.1 统一来源

管理员首页与数据统计使用同一套受角色范围约束的统计来源。服务端统计结果增加：

- `ordinaryPendingCount`：当前角色范围内普通待审数量；
- `counselorPendingCount`：当前角色有权查看的重点待审数量；
- `actionablePendingCount`：当前角色实际可处理的待审总数；
- `activeRoomCount`：当前角色范围内开放房间数量；
- `todayReservations`、`usingCount`、`noshowCount`。

导生管理员的房间数、预约数、使用数和排行全部遵循其“全院或具体楼栋”范围。

### 5.2 首页指标

首页优先展示与当前任务直接相关的指标：

- 当前队列待审数；
- 今日预约；
- 使用中；
- 开放功能房。

辅导员和超级管理员另显示普通待审与重点待审的分项入口。待处理反馈只在具备反馈处理权限时显示。

所有数字允许为 0，不使用 `0` 时回退到固定假数字的写法。

### 5.3 使用排行

使用排行统一返回：

- 房间标识与名称；
- 有效预约次数；
- 实际使用天数。

页面移除“预约次数除以 30”的伪使用率百分比。若未来需要真正使用率，应以可开放时长和实际占用时长为分母、分子另行设计。

模拟数据和 MySQL 数据必须返回相同字段结构，且仅显示有实际记录的房间；无数据时显示明确空状态，不铺满零值排行。

## 六、管理中心、账号设置与导航

### 6.1 管理中心

- “待审核”改为“普通预约审核”；
- “辅导员重点审核”改为“重点预约审核”，说明中明确由辅导员或超级管理员处理；
- 审批入口显示对应待办数量；
- 分组保持“审批与统计、预约与空间、宿生与信用、运营审核”；
- 增加足够底部留白，内容不得被固定导航遮挡。

### 6.2 账号设置

- 页面标题改为“账号与设置”；
- “网络诊断”改为“连接检查”，使用管理员可理解的连接状态和重试文案；
- 账号安全说明当前账号的安全处理方式，不展示开发配置；
- 避免重复显示相同角色信息。

### 6.3 底部导航

管理员的“审批、管理、我的”继续保持三项结构，但用替换当前页面的方式切换，不重新启动整个小程序页面栈。

现有学生原生标签栏不改动。管理员导航列表只保留一个来源，避免组件与全局自定义标签栏两套配置继续漂移。

## 七、视觉与可访问性要求

- 延续现有蓝色、白色卡片和圆角设计，不重做品牌风格；
- 普通与重点审核除颜色外还必须有文字标签；
- 审批按钮最小触控高度按约 44 像素设计，并保留足够间距；
- 主要说明文字提高与背景的对比度；
- 处理中、加载失败、无数据等状态不能只靠颜色表达；
- 使用现有真实图片资源或统一图标资源，不新增字符图标、表情或临时绘制图形。

## 八、数据与安全边界

- 普通导生只能请求和操作 `pending`；
- 辅导员和超级管理员可处理 `pending` 与 `counselor_pending`；
- 重点队列查询、待办数量和详情操作都必须由服务端再次校验角色；
- 楼栋范围由服务端管理员范围中间层控制，前端筛选不能代替权限控制；
- 审批成功后继续使用统一通知与实时状态更新机制；
- 不增加移动端账号管理、房间配置或系统配置能力。

## 九、验收标准

### 9.1 功能验收

- 导生管理员只看见普通队列，不能请求或处理重点队列；
- 辅导员默认看到重点队列，并可切换普通队列；
- 超级管理员可处理两类队列；
- 重点预约必须进入管理员详情后处理；
- 普通预约快速通过和详情处理均能刷新列表与数量；
- 拒绝原因必填，重复点击不会提交两次；
- 接口失败显示失败重试，不显示空状态；
- 管理员预约详情不存在宿生操作；
- 导生管理员统计严格符合其全院或楼栋范围；
- 首页与统计页的今日预约、待办和开放房间数据一致；
- 使用排行字段完整且不再显示伪百分比；
- 三个底部栏目切换不重启整个小程序页面栈。

### 9.2 自动检查

- 为普通、辅导员和超级管理员分别验证菜单、默认队列、可操作状态与越权拦截；
- 覆盖两类待办计数和楼栋范围；
- 覆盖模拟数据与标准数据的排行字段契约；
- 覆盖加载、失败、空状态、过期请求和重复提交；
- 覆盖管理员详情页的操作边界；
- 继续运行管理员小程序、移动端、跨端契约、安全和完整回归检查。

### 9.3 视觉验收

使用用户提供的 484×1050 左右手机视口作为对照尺寸，至少检查：

- 超级管理员普通队列和重点队列；
- 辅导员重点队列；
- 导生管理员普通队列；
- 管理中心；
- 数据统计；
- 管理员预约详情；
- 加载失败与真正空状态。

若微信开发者工具自动化能力不可用，必须明确记录限制，并使用静态页面检查、接口运行检查和现有截图对照补足，不得声称完成真实模拟器视觉回归。

## 十、明确不做

- 不在本轮增加批量审批；
- 不在小程序增加房间、楼栋、账号或开放规则配置；
- 不把海报审核、反馈处理等已有能力扩展成新的复杂流程；
- 不改变宿生预约自动审批和冲突判断规则；
- 不用固定假数据掩盖接口异常。
