## 二、实现方案：总体方针与技术路线

### 2.1 方针

1. **不推翻**：`server/src` 分层与 camelCase 命名、`YYYYMMDD_*.sql` + 预检脚本、`response.js` 封装、`adminScope` 二维模型、`auditTrailService` 哈希链、`checkinCredentialService` 签名——全部保留。
2. **叠加而非替换**：新能力以"新表 + 新 Util/Service + 在既有函数体内插入调用"的方式叠加。
3. **增量向后兼容**：
   - `response.js` 的 `code` **保持 HTTP 数字语义**（前端按数字分支），业务码以**新增字段** `businessCode` 输出，旧客户端忽略未知字段不受影响。
   - 新增数据库列一律 `DEFAULT NULL`/有默认值，旧版本读取不受影响。
   - `version` 乐观锁：请求未携带 version 时**退化为现有 `WHERE status` 条件更新**，保证蓝绿过渡期双版本行为一致。
4. **迁移**：沿用现有 `YYYYMMDD_*.sql` + `scripts/apply-*-migration.js` 预检幂等模式。

### 2.3 关键技术决策

1. **`response.js` 不破坏兼容**：`code` 继续为 HTTP 数字；业务码走新字段 `businessCode`。这是**必须**的——前端 `admin/src/utils/request.js` 与 `miniapp/utils/request.js` 按数字 code 分支。
2. **脱敏收口策略**：不在 SQL 层脱敏（会破坏楼栋筛选/排序），统一在 **Presenter/出口层**；`formatReservationRow(row, viewer)` 新增第二参数 `viewer`，旧调用方不传时**保持原行为**（避免蓝绿期新旧版本行为撕裂），随任务推进逐个调用点传入 viewer。R-16 用例保证无遗漏。
3. **临时授权挂点**：**不改** `utils/adminScope.js` 的纯函数 `normalizeAdminScope`；在 `middleware/adminScope.js.loadAdminScope` 已装载 `req.adminScope` 之后追加 `req.adminScope.capabilities`，并新增 `requireCapability()` 中间件导出供路由装配。
4. **会话撤销的地道做法**：`middleware/auth.js:21` 在 `status !== 'active'` 时返回 null → 交接事务里 `UPDATE admins SET status='disabled'` 即实现"撤销旧会话"；再于事务提交后 `redis.del('token:admin:'+oldAdminId)`（复用 `getRefreshTokenKey` 键规则）清除刷新令牌。无需引入新 session 表。
5. **围栏校验顺序**：必须在 `credentialService.consume()` **之前**校验——`consume` 会原子删除 nonce，若围栏失败后已消费，用户必须刷新凭证才能重试，体验受损。
6. **能力解析性能**：每请求查授权表有成本 → Redis 缓存 `admin:caps:<id>`（60s），授权/交接变更时主动 `del`。
7. **version 退化兼容**：`approve/reject` 若前端未传 version，退化为现有 `WHERE status=?` 更新并 `version=version+1`；两者都写轨迹。
